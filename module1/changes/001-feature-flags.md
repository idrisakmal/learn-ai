# 001 — Per-application feature flags

> As an application developer, I want feature flags per application, so that I
> can enable or disable functionality without deploying code changes.

**Notes:** ABOUT.md has listed this as *known to be coming* since Module 2 — a
`Flag` model related to `Application` — and `prisma/schema.prisma` carries a
commented extension point for it. The shape follows `Configuration` exactly:
ULID primary key, `applicationId` FK with `ON DELETE CASCADE`, and `name` unique
*per application* rather than globally. The value is a plain boolean, not opaque
`jsonb` — a flag that is neither on nor off is not a flag.

## Acceptance criteria

Each is one task, roughly one commit, and goes through all four stages before
the next one starts.

### 1. Create a flag

- **Given** a registered Application
- **When** `POST /api/v1/flags` is sent `{ applicationId, name, enabled }`
- **Then** the flag is stored with a generated ULID and returned with `201`; a
  second flag with the same `name` for the same Application is rejected with
  `409`, while the same `name` under a different Application succeeds
- **Status:** 🔄 in progress

### 2. Read an Application's flags

- **Given** an Application with flags
- **When** `GET /api/v1/applications/:id/flags` is requested
- **Then** its flags come back in creation order; an Application with no flags
  returns an empty list, and an unknown Application id returns `404` rather
  than an empty list
- **Status:** ❌ not started

### 3. Toggle a flag

- **Given** an existing flag with `enabled: true`
- **When** `PUT /api/v1/flags/:id` is sent `{ enabled: false }`
- **Then** only `enabled` changes — `name` and `applicationId` are untouched,
  matching the partial-`PUT` semantics the rest of the API already uses — and
  an unknown flag id returns `404`
- **Status:** ❌ not started

### 4. Toggle a flag from the Admin UI

- **Given** the Admin UI showing an Application
- **When** the administrator toggles one of its flags
- **Then** the change is sent to the API and the row is rebuilt from the
  response, so a rejected write never leaves the UI showing a value the service
  did not accept
- **Status:** ❌ not started

## Current task

### PLAN

#### Shape

A new `Flag` resource, mirroring `Configuration` in every structural respect.

```
Flag
  id             ULID, PK, generated by newId()
  applicationId  FK → applications.id, ON DELETE CASCADE
  name           VarChar(256)   ─┐ unique together
  enabled        Boolean         │ with applicationId
  createdAt/updatedAt            ┘
```

Two deliberate departures from `Configuration`, both in the direction of *start
small*:

- **No `comments` column.** No criterion in this work item mentions one, and a
  nullable column is a cheap migration to add later. Symmetry alone is not a
  reason to carry a field nothing reads.
- **`enabled` is required, with no database default.** A flag that was never
  given a value is a flag whose state nobody decided. The criterion sends it
  explicitly; the schema should insist on it.

#### Test strategy

Both suites run against real PostgreSQL, following the existing convention.

**`flag.service.test.ts`** — happy path, failure paths, and the edge case:

| Case | Asserts |
|---|---|
| Creates a flag under an application | id is 26 chars, `applicationId` matches, `enabled` round-trips |
| **Creates with `enabled: false`** | stores `false`, not `true` |
| Unknown `applicationId` | throws `NotFoundError` |
| Duplicate `name` in the same application | throws `ConflictError` |
| Same `name` under a different application | succeeds |

`enabled: false` is the edge case that gets got wrong. Any `input.enabled ?? true`,
`input.enabled || true`, or truthiness check silently flips a disabled flag on,
and every other test still passes. It gets its own case.

The cross-application case is what proves the constraint is the compound
`(applicationId, name)` and not a global unique on `name` — a mistake the schema
would otherwise hide until a second application arrived.

**`flag.routes.test.ts`** — the same behaviour through `app.inject()`, pinning
status codes:

| Case | Expects |
|---|---|
| `POST /api/v1/flags` valid body | `201`, body carries `name`, `enabled`, 26-char `id` |
| Body missing `enabled`, or `enabled: "yes"` | `400` |
| Unknown `applicationId` | `404` |
| Duplicate name, same application | `409`, message naming the flag |
| Same name, different application | `201` |

The 409 comes from a domain `ConflictError` thrown next to the query, not from
the central `P2002` net — so the message says which flag conflicted, matching
`mapUniqueNameError` in the other two services.

## Out of scope

Stated here so it does not get argued per task:

- **No `DELETE`.** The API has no delete endpoints at all, by choice, while
  there is no authentication. Flags do not get to be the exception.
- **No targeting, no rollout percentages, no per-user flags.** A flag is on or
  off for an Application. Anything else is a different product.
- **No authentication.** Still explicitly out of scope project-wide.
