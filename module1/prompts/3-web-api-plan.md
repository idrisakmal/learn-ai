## 3. Data Layer

### Prisma schema (`prisma/schema.prisma`)

- `datasource db` → `provider = "postgresql"`, `url = env("DATABASE_URL")`.
- `generator client` → `prisma-client-js`.

**Application**
- `id String @id` — ULID generated in app code (no `@default`).
- `name String @unique @db.VarChar(256)`
- `comments String? @db.VarChar(1024)`
- `createdAt DateTime @default(now())`
- `updatedAt DateTime @updatedAt`
- `configurations Configuration[]` (relation)
- `@@map("applications")`

**Configuration**
- `id String @id` — ULID in app code.
- `applicationId String`
- `application Application @relation(fields: [applicationId], references: [id], onDelete: Cascade)`
- `name String @db.VarChar(256)`
- `comments String? @db.VarChar(1024)`
- `config Json` — maps to PostgreSQL `jsonb`.
- `createdAt` / `updatedAt` as above.
- `@@unique([applicationId, name])` — name unique per application.
- `@@map("configurations")`

**Module 3 extension point (do NOT build now):** a future `Flag` model will add
`applicationId String` + relation to `Application`, mirroring `Configuration`. The existing
relations leave room for it with no schema rework.

### Migration workflow (Prisma Migrate)

- Development: `prisma migrate dev --name <change>` — creates a timestamped SQL migration in
  `prisma/migrations/`, applies it, and regenerates the client. Migrations are committed.
- Production/deploy: `prisma migrate deploy` — applies committed migrations only, never
  generates new ones.
- `prisma generate` runs after install (and is invoked by `migrate dev`).

### ID generation

- `src/lib/ids.ts` exports `newId()` → `ulid()` from the `ulid` package. Services call
  `newId()` and pass the id into `prisma.<model>.create({ data: { id, ... } })`. The DB
  never generates ids.

## 4. API Layer

All routes registered under the `/api/v1` prefix. Every request body / path param validated
with Zod **before** the service is called; validation failure → **400** with the Zod issues.

### Applications

| Method | Path                  | Success | Notes |
|--------|-----------------------|---------|-------|
| POST   | `/applications`       | 201     | Body: `{ name, comments? }`. 409 if `name` exists. |
| PUT    | `/applications/:id`   | 200     | Body: `{ name?, comments? }`. 404 if missing; 409 on name clash. |
| GET    | `/applications/:id`   | 200     | Returns app **plus `configurationIds: string[]`**. 404 if missing. |
| GET    | `/applications`       | 200     | Returns `Application[]` (no nested configs). |

**Application response shape**
```json
{
  "id": "01J...",
  "name": "billing",
  "comments": "prod billing service",
  "createdAt": "2026-07-24T10:00:00.000Z",
  "updatedAt": "2026-07-24T10:00:00.000Z"
}
```
The `GET /applications/:id` variant additionally includes `"configurationIds": ["01J...", ...]`
(obtained via `include: { configurations: { select: { id: true } } }`, then mapped to ids).

### Configurations

| Method | Path                     | Success | Notes |
|--------|--------------------------|---------|-------|
| POST   | `/configurations`        | 201     | Body: `{ applicationId, name, comments?, config }`. 404 if app missing; 409 if `name` exists for that app. |
| PUT    | `/configurations/:id`    | 200     | Body: `{ name?, comments?, config? }`. 404 if missing; 409 on name clash within the app. |
| GET    | `/configurations/:id`    | 200     | Returns the configuration. 404 if missing. |

**Configuration response shape**
```json
{
  "id": "01J...",
  "applicationId": "01J...",
  "name": "database",
  "comments": null,
  "config": { "host": "db.internal", "port": 5432, "ssl": true },
  "createdAt": "2026-07-24T10:00:00.000Z",
  "updatedAt": "2026-07-24T10:00:00.000Z"
}
```

### Zod schemas (per resource, in `*.schema.ts`)

- `createApplicationSchema` — `name` (1–256), `comments` (max 1024, optional).
- `updateApplicationSchema` — same fields, all optional; reject empty body.
- `createConfigurationSchema` — `applicationId` (ULID string), `name` (1–256),
  `comments?` (max 1024), `config` (`z.record(z.string(), z.unknown())` — a JSON object).
- `updateConfigurationSchema` — `name?`, `comments?`, `config?`; reject empty body.
- Param schemas — `{ id: z.string() }` (ULID-shaped).

### Status-code contract

| Situation                         | Code |
|-----------------------------------|------|
| Resource created                  | 201  |
| Read / updated / list             | 200  |
| Request body/param invalid        | 400  |
| Referenced/target resource missing| 404  |
| Unique constraint violated        | 409  |
| Unexpected error                  | 500  |

## 5. Configuration & Environment

`src/config/env.ts`:
- Define a Zod schema: `DATABASE_URL` (url, required), `PORT` (coerced number, default 3000),
  `LOG_LEVEL` (enum `fatal|error|warn|info|debug|trace`, default `info`), `NODE_ENV`
  (enum `development|test|production`, default `development`).
- Parse `process.env` at import time; on failure, print the Zod issues and `process.exit(1)`
  (fail-fast). Export a typed, frozen `env` object.
- Env values are loaded via Node's built-in `--env-file=.env` flag in the scripts (no
  `dotenv` dependency). Prisma CLI reads `.env` automatically.

`.env.example` (committed):
```
DATABASE_URL="postgresql://user:password@localhost:5432/config_service?schema=public"
PORT=3000
LOG_LEVEL=info
NODE_ENV=development
```

## 6. Testing Strategy

- **Framework:** Vitest. Config in `vitest.config.ts` (`environment: 'node'`).
- **Placement:** `*.test.ts` beside each unit (per spec). No top-level `test/` folder until a
  shared helper or integration suite genuinely needs one.
- **Route tests** use `buildApp()` + Fastify's `app.inject()` — no network listener.
- **Integration tests** run against a **real PostgreSQL** database (a dedicated
  `config_service_test` DB), migrated with `prisma migrate deploy` before the suite, and
  cleaned between tests (truncate tables in FK-safe order).

**~80% scenarios per module:**
- `env.test.ts` — valid env parses; missing `DATABASE_URL` exits/throws; bad `PORT` rejected.
- `ids.test.ts` — `newId()` returns a 26-char ULID; two calls are unique and monotonic.
- `application.service.test.ts` — create, update, get-with-config-ids, list; duplicate name → conflict; update missing → not-found.
- `application.routes.test.ts` — happy paths return 201/200; invalid body → 400; duplicate name → 409; missing id → 404.
- `configuration.service.test.ts` — create under app; create under missing app → not-found; duplicate name-per-app → conflict; update; get.
- `configuration.routes.test.ts` — status-code contract across create/get/update, including the `config` jsonb round-trip.

## 7. Architectural Patterns & Conventions

- **Error handling:** services throw typed domain errors (`NotFoundError`, `ConflictError`
  from `lib/errors.ts`). A single Fastify `setErrorHandler` maps: Zod error → 400, domain
  errors → 404/409, Prisma known errors (`P2002` unique → 409, `P2025` not-found → 404),
  everything else → 500. Route handlers stay thin.
- **Request lifecycle:** route validates with Zod → calls service with plain typed args →
  service uses the shared Prisma client → route serialises the result and sets the status.
- **Prisma client:** one instance created in `src/db/prisma.ts` and imported where needed;
  closed on server shutdown (`app.addHook('onClose', ...)`).
- **Logging:** Fastify's built-in pino at `LOG_LEVEL`; request logging enabled.
- **ID generation:** always via `lib/ids.newId()`; never DB defaults.
- **TypeScript:** `strict: true`, no implicit `any`, `NodeNext` module resolution.

## Assumptions

- ULIDs are generated app-side (spec is explicit); DB has no id default.
- `config` is always a JSON **object** of name/value pairs (not an array or scalar).
- `PUT` is a partial update (patch semantics) that rejects an empty body; it is not a full
  replace requiring every field.
- No pagination on `GET /applications` for now (not in spec).
- No auth (explicitly out of scope).

## Resolved Decisions (Entry 3)

The plan's open questions were answered before execution:

1. **Extra dependencies:** `tsx`, `eslint`, and `typescript-eslint` are **approved** and
   folded into §1 and §8. `pino-pretty` is **not** added.
2. **PUT semantics:** **partial update / patch** — send only the fields to change; omitted
   fields are untouched; an empty body is rejected.
3. **`GET /applications` payload:** **bare applications** — `configurationIds` appears only
   on `GET /applications/:id`, per the spec.
4. **DELETE endpoints:** **intentionally omitted** — none in the spec, none added now.
5. **`config` constraints:** **any valid JSON object** — no size or nesting cap for now.
